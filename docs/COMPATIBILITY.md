# 兼容机制与验证范围

## 从版本校验改为接口适配

旧实现同时绑定游戏文件 SHA、模块 MVID 和混淆符号名。任何客户端重建都需要重新打包，即使钓鱼功能没有变化。

0.4.0 的发行包只包含本项目源代码、接口结构与单向指纹以及通用编译／注入依赖。连接流程：

1. 找到唯一的 Windows 游戏进程，读取其安装目录的程序集元数据。
2. 用 `compatibility/contract.json` 解析 35 个所需类型与 111 个成员。稳定名称与签名直接核对；混淆成员按结构、规范化方法指纹、调用位置区分。解析缓存仅保留到本次连接，不保存游戏代码。
3. 类增加无关成员时，可用多个独立方法指纹定位；相同类型的字段根据使用位置区分，不依赖声明顺序。不唯一、缺失或形状不符都拒绝猜测。
4. 核对鱼稀有度、鱼／鱼饵类别、动态读取的表属性，六种原生解析回执入口，以及独立的锁定状态回执入口。
5. 在内存中用本机的只读元数据引用编译项目自己的 Runtime，内嵌 Harmony。此步骤使用 [Roslyn 编译 API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.csharp.csharpcompilation)，不调用外部 SDK，也不执行客户端程序集。
6. 检查通过后才注入。游戏内校验本次生成组件对应的 MVID，防止“文件已更新、游戏仍运行旧进程”的竞态；这是针对当前连接生成的身份，不是发行包对某个游戏版本的锁定。
7. 检查 UI、帧回调和接口后进入等待钓点状态；用户点击开始才执行自动化。反射接口在游戏内缓存，按帧操作不会重复扫描元数据或编译。

`compatibility.json` 包含 `Status`、当前 MVID、识别数量、改名数量和失败说明。MVID 用于诊断，不包含账号身份。没有远程映射下载或静默执行网络脚本。

检查涵盖实际客户端的帧入口、混淆绑定、结算与升级弹窗、常驻货币栏分类、昼夜切换标志、六种原生网络回执、出售 DTO 的实例 ID／数量／类型、独立保留规则、MAX／MIN、锁定保护及确认解锁、钓区／移动接口、船外朝向、鱼饵具体库存、游戏时钟、地图加载协程、往返入口及依赖闭包。离线检查不注入游戏，不发送请求。

独立测试还覆盖版本标识变化、重命名、字段／方法重排、增加无关方法、接口破坏和歧义拒绝。公开 CI 使用项目自行生成的测试程序集，不需要也不上传游戏 DLL。

原有钓鱼决策、保护及控制租约回归为 14,979 条断言；其数量包含随机时序和库存组合断言，并不代表 14,979 种实机场景。

0.4.0 / Runtime10 合并 PR #2 与自动靠岸链路后，两个客户端均重新通过解析、编译和 83 项离线 ABI 检查，包含体型、原生解锁入口、最终出售请求保护及编译产物与声明 Runtime 身份一致性。

## 实机边界

0.3.2 已在没有导航网格的钓场完成原生角色行走、到位抛竿、8次收获，并在一次昼夜切换后继续钓鱼。用户确认试用正常；本机日志对应 Runtime9。只保留上锁鱼的实际批量出售与6小时到期往返仍为 `source_implemented_pending_runtime`，此次短程运行不代表这些场景已经通过。

0.4.0 的解锁→出售→继续钓鱼闭环仍需加载新版组件后实机验收。此前发现直接提交锁定鱼会导致出售被服务器拒绝，本次增加原生解锁确认链路；离线检查不等同于服务器接受出售。

试用建议：首次运行观察普通收获、连续十竿、特殊鱼技能、停止／关闭窗口，然后核对满背包出售、鱼饵到期和昼夜切换。遇到错误保留诊断，不反复注入。

当混淆方式、调用结构、钓鱼逻辑或网络协议发生根本变化时，维护者仍需分析更新。不会保证任意未来版本自动兼容，也不会为了适配而放宽保留鱼和请求确认规则。

## 0.3.2 进图移动修复

实机报告揭示旧导航前提不成立：Map3010_012／地图组7、AutoApproach=true，但ActionCount=0，10秒后报无可用行走路径。导航不可用时现使用游戏原有CharController方向和SetMoveStart输入，原生控制器负责速度／重力／碰撞。新增32条实际FishingNavigation协调器回归，覆盖缺失／禁用／离网格、转向后可抛竿、取消、碰撞停滞和重新开启。该回归使用测试宿主，不代表Unity实机通过。随后自然实机日志确认 nav=missing、CharController 开始行走，约1秒后停止移动并正常抛竿；完成8次收获和一次昼夜切换后续钓。原始日志仅在本机保留，不随公开仓库发布。
